# KIMI_CONTEXT — LNK

Краткий входной документ для работы над репозиторием `yachtsman13/LNK`.
Сначала читать этот файл, затем открывать только документы и код, необходимые для задачи.

## Назначение проекта

Система лаборатории неразрушающего контроля: журналы и реестры, планирование работ,
контроль сроков, документы Word, обмен между рабочими местами и резервное копирование.
Проект сочетает Python, Excel/VBA, файлы Excel и шаблоны Word.

## Карта документации

- `СОСТАВ.md` — основная архитектура, назначение каталогов, модулей и скриптов.
- `ТЗ/Задачи_по_проекту_2026-11.md` — актуальный список задач заказчика и их статусы.
- `ИЗМЕНЕНИЯ.md` — история изменений; читать последние записи или искать нужную версию,
  не загружать весь файл без необходимости.
- `ТЗ/Что_осталось.md` и `ТЗ/Что_дослать.md` — старые списки остатков и материалов;
  сверять с кодом и новым списком задач, так как часть пунктов уже закрыта.
- `ТЗ/ТЗ_Система_ЛНК.md` — подробное техническое задание; использовать только нужный раздел.
- `ТЗ/Проработка_*.md` — проектные решения по отдельным подсистемам.
- `CLAUDE.md` — очень большой справочный документ; читать только найденные поиском фрагменты.

## Основные каталоги

- `Макросы/` — исходники VBA.
- `Макросы/Для_импорта/` — модули в кодировке cp1251 для импорта в Excel.
- `scripts/` — сборка, миграция и автоматические проверки.
- `Реестры/` — рабочие данные Excel; не изменять без необходимости задачи.
- `Шаблоны/` — шаблоны документов Word.
- `Лента/` — интерфейс ленты Excel и связанные файлы.
- `ТЗ/` — требования, образцы, статусы и проектные решения.
- `Приложение/` — файлы прикладной части проекта.

## Проверки

Выбирать только относящиеся к изменению проверки:

- `scripts/check_vba.py` — проверки VBA;
- `scripts/check_data.py` — структура и связность книги данных;
- `scripts/check_templates.py` — соответствие полей шаблонов и данных;
- `scripts/check_ribbon.py` — проверки ленты.

Перед запуском убедиться в наличии необходимых входных файлов. Скрипты сборки,
особенно `build_data.py` и `migrate.py`, не запускать без понимания их побочных эффектов.
Полный набор доступных проверок выполнять один раз после завершения правок, а не после
каждого небольшого изменения.

## Критические правила

1. Не смешивать UTF-8-исходники и cp1251-файлы для импорта VBA.
2. Для подготовки импортируемых модулей использовать штатные скрипты проекта.
3. Не выдумывать формы нормативных документов: если нужен отсутствующий образец,
   остановиться и запросить его.
4. Не изменять мигрированные записи, рабочие реестры и бинарные файлы без явной необходимости.
5. Не проводить общий рефакторинг вместе с локальной задачей.
6. Обновлять статусы задач, историю изменений и связанную документацию по существу.
7. Не добавлять секреты, локальные пути с личными данными, временные файлы и копии баз.
8. Не использовать force push и не переписывать историю Git.

## Текущее состояние и возможные задачи

По ноябрьскому списку значительная часть пунктов закрыта в версиях 3.67–3.84.
Перед началом любой задачи проверять код и свежие записи истории, а не полагаться только
на старые документы остатков.

В документации упоминались ожидающие материалов или решений владельца работы:
сопроводительное письмо ВД, бирки на стеллаж, сверка норм вибрации. В старом списке также
указаны импорт журнала и специалистов из Excel и раздел системы менеджмента; их фактическое
состояние нужно сначала проверить, чтобы не повторить уже выполненную работу.

## Ограничения облачной проверки

В Linux доступны Python- и статические проверки. Полноценное выполнение VBA, поведение Excel,
формирование и внешний вид документов Word, печать и взаимодействие со съёмными носителями
могут потребовать проверки на Windows. В итоговом отчёте отдельно указывать автоматические
проверки и то, что владельцу нужно проверить вживую.
