# Система ЛНК — постоянные правила проекта

## Язык
**Всё общение с заказчиком — только по-русски.** Ответы, пояснения,
сообщения об ошибках. В коде и документации проекта — тоже русский:
имена функций, переменных, комментариев уже написаны так, продолжать так же.

## Условия у заказчика (не меняются)
- Прав администратора нет. Ставить ничего нельзя, portable-программы можно.
- Сети между рабочими местами нет — обмен только файлами (флешка, общая папка).
- Office 2016, AutoCAD, Acrobat. Windows 11.
- Рабочих мест 3, в перспективе 6.

## Как устроена программа
`Приложение/ЛНК.html` — один самодостаточный файл, открывается с диска или
флешки, без установки и без сети. Собирается скриптом:

    python3 scripts/export_json.py   # книга Excel      → Приложение/данные.json
    python3 scripts/export_ppr.py    # план-график ППР  → Приложение/ппр.json
    python3 scripts/build_app.py     # шаблон+данные    → Приложение/ЛНК.html

**Править только `Приложение/шаблон.html`**, потом пересобирать.
`ЛНК.html` — сборка, руками не трогать.

Данные живут в памяти браузера (localStorage). Ключи **без номера версии** —
иначе новая версия программы откроется пустой.

Замерено: предел localStorage ~5 МБ, занято 235 КБ на 315 записей со
справочниками (~766 символов на запись) — запас ~6500 записей. Предел
молчаливый, поэтому в программе есть счётчик заполнения и предупреждение.
Упрутся — переносить на IndexedDB (в file:// работает, квота ~1 ГБ).

File System Access API (`showDirectoryPicker`) **из file:// работает** —
проверено вызовом: возвращает AbortError (нет пользователя), а не
SecurityError. На этом сделаны автокопии в выбранную папку. В Firefox
API нет — там ручная копия в папку загрузок.

## Правила работы
1. **Ничего не выдумывать.** Формы документов, расшифровки кодов, правила
   нумерации берутся только из присланных заказчиком файлов. Нет образца —
   поле оставляется пустым с подсказкой, а не заполняется догадкой.
   Предположения называть предположениями прямо.
2. **Проверять, а не полагаться.** Изменения в приложении проверяются
   безголовым Chromium (playwright лежит в `$(npm root -g)/playwright`,
   Chromium в `/opt/pw-browsers`), вёрстка — замером, а не на глаз.
   Выгрузка в Word — `scripts/проверка_docx.py`, в Excel —
   `scripts/проверка_xlsx.py` (обе ловят порядок элементов: Office не
   говорит «переставлен элемент», он объявляет файл повреждённым).
   Постраничная вёрстка акта — `scripts/проверка_печати.py` по готовому
   PDF (pymupdf): наличие keepNext/keepLines и неразрывных пробелов в
   разметке ничего не доказывает, проверять надо результат на страницах.
   Проверяет три правила: нет листа с одними подписями, разделы не
   разорваны, строки не кончаются висящим словом.
3. **Наименование организации** в документах — только нейтральное, из поля
   настроек. Никаких иных характеристик заказчика в текстах и файлах.
   Все данные в примерах — образец.
4. Ветка разработки: `claude/ndt-lab-optimization-2rpoge`.

## Что сделано и что ждёт заказчика
Сделано: журнал, справочники, пульт, обмен между местами с переносом
удалений, резервная копия, фильтры и сортировка, автоматическая нумерация
протоколов и актов (право выдачи — эстафета), акт о проведении работ по
форме заказчика с выгрузкой в Word, выгрузка разделов и всей базы в
настоящий .xlsx, автокопии в выбранную папку с поколениями и контроль
заполнения хранилища, раздел «План работ» (ППР) с отметками о выполнении и выгрузкой в Word,
раздел «Проверка данных» (расхождения внутри самой базы, включая дубли
карточек объектов по номеру), справочник заказывающих подразделений с
контрактами по годам, карточка лаборатории (организация, аттестация со
сроками, методы, произвольные сведения, ответственные лица, область
аттестации по СДАНК), сроки лаборатории на пульте, менеджер задач с
контролем исполнения и отчётом за период, Паспорт ЛНК (форма из
СДАНК-01-2020, уточнена по присланному настоящему бланку «Редакция № 6»)
с выгрузкой в Word, импорт из Excel для объектов и приборов (свой
шаблон-таблица, свой разбор .xlsx без библиотек), подразделение на
карточке объекта с автоподстановкой в акт, инструктаж по охране труда у
специалиста (раз в 90 дней), справочники нормативных документов и
помещений для разделов 9–10 паспорта, праздники и переносы выходных,
нумерация списков СДАНК из текста документа, лист ознакомления
сотрудников ЛНК в паспорте, категория прибора для разделов 5–8 паспорта
(полная Форма 2 СДАНК, не только заводской номер и поверка), область
аттестации и помещения из реального паспорта (разделы 3, 4, 10).

`.docx` и `.xlsx` собираются своим кодом (ZIP без сжатия, `zipStore`) —
библиотек нет и быть не может, программа остаётся одним файлом без сети.

План ППР: 44 позиции из книги заказчика, 2026-2030. Периодичность —
доля года + вид ТО; доля подтверждена разметкой, номера ТО-1…ТО-4 не
расшифровываются (в книге их значения не написаны). Отметки о выполнении
— свой реестр `lnk_ppr`, ходит в обмене и в копии.

Проверка данных делит найденное на три уровня: ошибка (не может быть верным),
внимание (обычно недоделка), наблюдение (порядок заказчика неизвестен — не
называть ошибкой). Спорное в первые два уровня не попадает.

Акт: шапка о свидетельстве по центру курсивом (из настроек ЛНК); тип и
реквизиты контракта из карточки подразделения по году акта; разделы
перечня пронумерованы; номера протоколов неразрывны (в Word —
`w:noBreakHyphen`, не пробелы); подписи трёх ролей (руководитель
экспертной организации с организацией второй строкой, руководитель работ,
специалисты); колонка должностей — по самой широкой строке в ней (замер
через canvas настоящим шрифтом документа, `твипыСтроки`/`ширинаДолжностей`),
с пределом 4536 твипов = 8 см ШИРИНЫ колонки (не «8 см от края листа» —
при таком чтении предел выходил 5,25 см и «Заместитель начальника ЛНК»
переносился); должности по центру, фамилии вправо; `keepNext` + `cantSplit`
не дают подписям уехать на пустой лист; `keepLines` не даёт разорвать
раздел перечня между страницами. В HTML те же правила — `break-after:avoid`
на последнем разделе (класс «последний») и `break-inside:avoid` на разделах
и таблице подписей.

Номера объектов при группе одного наименования: сначала все заводские,
затем все регистрационные. При разнотипных объектах номера остаются при
своём объекте.

Падежи не склоняются автоматически. Для подразделения — поле «предложная
форма» в карточке. Для объектов — словарь `lnk_padezh`: форма запоминается
за НАИМЕНОВАНИЕМ (уникальных 127 на 315 записей), ходит в обмене,
заполняется в акте под фразой об объектах.

Висячие слова: `типографика()` ставит неразрывный пробел после
однобуквенных слов и коротких предлогов, между числом и единицей, после
знака №, перед «г.», между инициалами и фамилией. Применяется и в Word, и
на экране. Поля акта должны быть `display:inline` — при `inline-block`
Chromium переносит строку по границе блока и неразрывный пробел не спасает.

Размерность со степенью (м³, см²) — закрытый список единиц
(мм|см|дм|км|м)([23]), `разбитьСтепени`; в Word `w:vertAlign superscript`.
В поле ввода сохраняется обычное «м3» (innerText не видит <sup>).

Порядок элементов OOXML, на котором уже трижды ловился: `tabs` ПЕРЕД
`spacing` в pPr; `tblLayout` ПОСЛЕ `tblBorders` в tblPr; `vertAlign` ПОСЛЕ
`sz`/`szCs` в rPr. Таблица подписей требует `tblLayout fixed` — иначе Word
пересчитывает ширины по содержимому и переносит должность на вторую
строку.

Акт, число документов: при одном документе по методу — единственное число
названия и один знак «№». Формы единственного числа (`ДОК_ИМЕНА_ЕД`) — мой
черновик, в образцах их не было; правятся и хранятся отдельно от
множественных.

Право выдачи номеров закрепляется автоматически за местом, которое первым
выдаёт номер, если оно ничьё (`правоЕслиНичьё`). Блокировка остаётся только
когда право у другого места — иначе на первом запуске это выглядит поломкой.

Номер акта в форме записи выбирается: существующий (список от большего
номера), новый (следующий по порядку) или без акта. Объекты в списке — со
строкой «наименование, зав. № …, рег. № …», поэтому поиск по номеру
работает штатным механизмом браузера; при сохранении строка разбирается, а
карточка ищется по имени ВМЕСТЕ с заводским номером.

Задачи (`lnk_tasks`): одна сущность со сроком, периоды — шесть
представлений одного списка (`границыПериода`), не шесть списков. Горизонт
планирования — отдельное поле. Состояния: назначена → принята → выполнена →
закрыта, с возвратом на доработку; ставит и принимает место с признаком
`начальник` в `getWS()`. Перенос срока ОБЯЗАН сохранять `срок_первый` —
иначе отчёт всегда показывает сто процентов в срок (`вСрок`).

Производные задачи (`производныеЗадачи`) НЕ хранятся, а вычисляются из
плана ППР (срок — последний день месяца), дат поверки и сроков лаборатории.
Отмечаются в своих разделах: отметка в ППР сразу меняет их состояние в
списке задач. Журнал в производные не включён намеренно — он уже в
«Проверке данных», иначе дубль.

Повторяющиеся задачи: при приёме работы `продолжитьПовтор` создаёт
следующую со сдвинутым сроком, не выходя за `повтор_до`; защита от
задвоения — по паре `родитель` + `срок`.

Ответы заказчика по задачам: отчёт по форме (пришлёт позже — пока
внутренний вид), задачи назначает начальник, контроль исполнения нужен.

СДАНК-01-2020 и СДАНК-02-2020: заказчик прислал оба документа целиком —
прочитаны полностью (40 и 38 страниц), факты взяты дословно, без
домыслов. Сделано: классификаторы объектов (12 категорий, 63
подкатегории) и методов НК (12 категорий) из приложений — вшиты в
карточку лаборатории отдельными полями «область аттестации» (объекты +
методы), не путать со старым полем методов журнала, которое осталось
для сверки с тем, что реально делает лаборатория; ответственные лица
раздела 1 паспорта; аттестация специалиста дополнена датой и органом,
выдавшим удостоверение (нужны для Формы 1 паспорта); отдельный блок
«удостоверение о проверке знаний правил безопасности» у специалиста —
СДАНК-02-2020 прямо требует его отдельно от квалификационного, без него
квалификационное недействительно; Паспорт ЛНК — печатная форма (все 11
разделов) и выгрузка в Word, разделы 1–5, 9–10 из настоящих данных
программы, 6–8 и 11 — с честной пометкой, что заполнить нечем (раздел 5
на эти категории не делит, а передвижных лабораторий в программе нет
вовсе). Номер свидетельства об аттестации ЛНК
— «№ ЛНК-ХХХ Х ХХХХ» (раньше в программе стоял другой, придуманный
формат — исправлено); срок действия свидетельства НЕ фиксирован
документом, его каждый раз определяет комиссия по аттестации — программа
больше не предполагает срок сама. Подробности, включая точный текст
классификаторов и что именно взято из каких приложений — в
`ТЗ/СДАНК_что_нужно.md`.

Импорт из Excel (объекты, приборы): свой шаблон-таблица (кнопка рядом с
импортом создаёт пустой .xlsx с колонками из `REGS[kind].fields`), не
исходная книга заказчика — там формулы и разметка под `export_json.py`,
смешивать с формой ручного заполнения нельзя. Разбор .xlsx свой, без
библиотек: ZIP-каталог по сигнатурам PK руками (`zipЧитать`/`zipТекст`),
распаковку DEFLATE делает браузер (`DecompressionStream('deflate-raw')`)
— своего инфлейта не пишу, слишком велик риск ошибиться на настоящем
файле. Два бага, пойманных на РЕАЛЬНОМ файле от openpyxl (Excel мог бы
дать те же формы): тип ячейки `t="inlineStr"` — с заглавной, регэксп на
`[a-z]+` его не ловил; кириллица приходит как числовые ссылки
(`&#1053;`), не сырым UTF-8 — оба случая не годится проверять на файле
собственной генерации, там этих форм не было. Колонки сопоставляются по
ТЕКСТУ заголовка с `f.l`, не по номеру — переставленные столбцы не
ломают импорт. Даты СИ разбираются и как серийное число Excel (день 0 =
30.12.1899, поправка 25569), и как текст «31.12.2026». Импорт только
ДОБАВЛЯЕТ записи; проверка данных на дубли объектов теперь настоящая, а
не по совпадению имя+зав (это давало ложные срабатывания на карточках,
различающихся регистрационным номером): одинаковый непустой
зав./рег. номер у разных карточек — ошибка, одинаковое имя вовсе без
номеров — только наблюдение.

Подразделение у объекта (`подразделение` в карточке объекта, тип поля
`podr` — выпадающий список из справочника «Подразделения», значение —
ссылка на карточку, как и `a.подр` у акта, не текст): каждый объект
«принадлежит» подразделению, поэтому акт при первом открытии сам
подставляет `a.подр`, если у ВСЕХ объектов акта оно одно
(`автоподразделениеАкта`) — только при первом открытии, повторно не
трогает, если потом выбрали руками другое. Если объекты акта вразнобой
по подразделениям — ничего не подставляет и предупреждает текстом, какие
подразделения разные (`подразделенияАкта`, поиск по `объект_ид` в `O`).
В форме журнальной записи то же самое поле подставляется в `e_подразделение`
через `objHint()`, но только если поле ещё пустое — не переписывает
вписанное руками. Импорт объектов из Excel понимает колонку
«Заказывающее подразделение» как ТЕКСТ (название карточки), а не id —
ищет карточку по точному совпадению наименования (без учёта регистра);
не нашёл — оставляет пустым и перечисляет ненайденные названия в
диалоге подтверждения, а не подставляет что попало.

Инструктаж по охране труда — со слов заказчика, отдельный документ от
удостоверения ПБ (не путать: ПБ — это «проверка знаний правил
безопасности» из СДАНК-02-2020, инструктаж — общий, по ТК РФ).
Периодичность — раз в 90 дней (`ИНСТРУКТАЖ_ПЕРИОД_ДНЕЙ`), заказчик
подтвердил именно так, в СДАНК такого срока нет. Хранится ОДНА дата —
«прошёл в последний раз» (`инструктаж_дата` у специалиста), без журнала
прохождений: заказчик прямо сказал, что история не нужна. Срок «до»
считается прибавлением периода и оценивается через уже готовый
`срокЛаб()` (тот же bad/warn/ok, что у аттестации ЛНК — не плодил
отдельную копию). Проверка данных: дата не внесена — «внимание» (могли
не записать), а вот просрочка — «ошибка» (как просроченная поверка).
Заведено в `производныеЗадачи()` — попадает в «Задачи», если дата
внесена; без даты задачу строить не из чего, это только в «Проверке
данных». Статус виден и в списке специалистов отдельной колонкой.

Срок «до», если выпадает на нерабочий день, сдвигается на ближайший
рабочий день назад (по прямому указанию заказчика: инструктаж в
нерабочий день не проводится). Сначала это считалось просто от
субботы/воскресенья; заказчик прислал производственные календари на
2026 и 2027 год (КонсультантПлюс), и теперь список настоящий —
`ПРАЗДНИКИ_ПО_УМОЛЧАНИЮ`. Даты сверены арифметически: список нерабочих
дней вместе с обычными выходными даёт ровно 118 дней на каждый год —
столько показано в самих календарях, совпадение точное на оба года.
Редактируется в карточке лаборатории (блок «Праздники и переносы
выходных», своя таблица дат с видом «нерабочий»/«рабочий» — второе для
случая вроде рабочей субботы 20.02.2027). Хранится как `л.праздники`,
`null` (не `[]`) отличает «ещё не трогали» (тогда `getЛаб()` каждый раз
подставляет даты по умолчанию) от «сохранили пустым нарочно» (тогда
список действительно пуст). `нерабочийДень(iso)` сначала смотрит на
переопределение в списке, иначе — обычный день недели;
`ближайшийРабочийНазад` идёт по календарю назад, пока не найдёт рабочий
день (до 15 шагов, чтобы не зациклиться, если данных на нужный год нет).
На 2028 год и далее список не продлевается сам — нужен новый календарь
от заказчика.

Область аттестации — виды деятельности (СДАНК_ДЕЯТЕЛЬНОСТЬ): третья
