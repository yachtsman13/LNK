# Система ЛНК — постоянные правила проекта

## Язык
**Всё общение с заказчиком — только по-русски.** Ответы, пояснения,
сообщения об ошибках. В коде и документации проекта — тоже русский:
имена функций, переменных, комментариев уже написаны так, продолжать так же.

## Условия у заказчика (не меняются)
- Прав администратора нет. Ставить ничего нельзя, portable-программы можно.
- Сети между рабочими местами нет — обмен только файлами (флешка, общая папка).
- Office 2016, AutoCAD, Acrobat. Windows 11.
- Рабочих мест 3, в перспективе 6.

## Как устроена программа
`Приложение/ЛНК.html` — один самодостаточный файл, открывается с диска или
флешки, без установки и без сети. Собирается скриптом:

    python3 scripts/export_json.py   # книга Excel      → Приложение/данные.json
    python3 scripts/export_ppr.py    # план-график ППР  → Приложение/ппр.json
    python3 scripts/build_app.py     # шаблон+данные    → Приложение/ЛНК.html

**Править только `Приложение/шаблон.html`**, потом пересобирать.
`ЛНК.html` — сборка, руками не трогать.

**Номер версии поднимать при каждой выдаче файла заказчику.** Заказчик
указал: версия в шапке стояла «v3.0» месяцами, хотя программа менялась
почти каждый день, — по ней невозможно понять, обновился файл или нет.
Номер лежит литералом в `scripts/export_json.py` (`"версия": "3.0"`),
оттуда попадает в `Приложение/данные.json` и показывается в шапке
(`DB.версия`) вместе с датой сборки (`DB.собрано`, там же). Менять надо
ОБА: пересобрать `данные.json` нечем без книги Excel, поэтому правится
литерал и заново гоняется `export_json.py`, либо, если книга не
пересобиралась, значение правится прямо в `данные.json` — оно там
информационное.

Поднимать версию безопасно, проверено по коду: номер попадает в
сохранённые записи только как штамп (`baseVersion` у журнала, `версия` у
справочников), а `loadJournal`/`loadReg` читают `rows` независимо от
него. Ключи хранения версии не содержат (см. выше) — данные заказчика от
смены номера не теряются.

Данные живут в памяти браузера (localStorage). Ключи **без номера версии** —
иначе новая версия программы откроется пустой.

Замерено: предел localStorage ~5 МБ, занято 235 КБ на 315 записей со
справочниками (~766 символов на запись) — запас ~6500 записей. Предел
молчаливый, поэтому в программе есть счётчик заполнения и предупреждение.
Упрутся — переносить на IndexedDB (в file:// работает, квота ~1 ГБ).

File System Access API (`showDirectoryPicker`) **из file:// работает** —
проверено вызовом: возвращает AbortError (нет пользователя), а не
SecurityError. На этом сделаны автокопии в выбранную папку. В Firefox
API нет — там ручная копия в папку загрузок.

## Правила работы
1. **Ничего не выдумывать.** Формы документов, расшифровки кодов, правила
   нумерации берутся только из присланных заказчиком файлов. Нет образца —
   поле оставляется пустым с подсказкой, а не заполняется догадкой.
   Предположения называть предположениями прямо.
2. **Проверять, а не полагаться.** Изменения в приложении проверяются
   безголовым Chromium (playwright лежит в `$(npm root -g)/playwright`,
   Chromium в `/opt/pw-browsers`), вёрстка — замером, а не на глаз.
   Выгрузка в Word — `scripts/проверка_docx.py`, в Excel —
   `scripts/проверка_xlsx.py` (обе ловят порядок элементов: Office не
   говорит «переставлен элемент», он объявляет файл повреждённым).
   Постраничная вёрстка акта — `scripts/проверка_печати.py` по готовому
   PDF (pymupdf): наличие keepNext/keepLines и неразрывных пробелов в
   разметке ничего не доказывает, проверять надо результат на страницах.
   Проверяет три правила: нет листа с одними подписями, разделы не
   разорваны, строки не кончаются висящим словом.
3. **Наименование организации** в документах — только нейтральное, из поля
   настроек. Никаких иных характеристик заказчика в текстах и файлах.
   Все данные в примерах — образец.
4. Ветка разработки: `claude/ndt-lab-optimization-2rpoge`.

## Что сделано и что ждёт заказчика
Сделано: журнал, справочники, пульт, обмен между местами с переносом
удалений, резервная копия, фильтры и сортировка, автоматическая нумерация
протоколов и актов (право выдачи — эстафета), акт о проведении работ по
форме заказчика с выгрузкой в Word, выгрузка разделов и всей базы в
настоящий .xlsx, автокопии в выбранную папку с поколениями и контроль
заполнения хранилища, раздел «План работ» (ППР) с отметками о выполнении и выгрузкой в Word,
раздел «Проверка данных» (расхождения внутри самой базы, включая дубли
карточек объектов по номеру), справочник заказывающих подразделений с
контрактами по годам, карточка лаборатории (организация, аттестация со
сроками, методы, произвольные сведения, ответственные лица, область
аттестации по СДАНК), сроки лаборатории на пульте, менеджер задач с
контролем исполнения и отчётом за период, Паспорт ЛНК (форма из
СДАНК-01-2020, уточнена по присланному настоящему бланку «Редакция № 6»)
с выгрузкой в Word, импорт из Excel для объектов и приборов (свой
шаблон-таблица, свой разбор .xlsx без библиотек), подразделение на
карточке объекта с автоподстановкой в акт, инструктаж по охране труда у
специалиста (раз в 90 дней), справочники нормативных документов и
помещений для разделов 9–10 паспорта, праздники и переносы выходных,
нумерация списков СДАНК из текста документа, лист ознакомления
сотрудников ЛНК в паспорте, категория прибора для разделов 5–8 паспорта
(полная Форма 2 СДАНК, не только заводской номер и поверка), область
аттестации и помещения из реального паспорта (разделы 3, 4, 10),
производные задачи в отчёте по задачам, объект и заметки у задачи,
предупреждение о задачах на неделю вперёд на пульте, проверка дублей
приборов по заводскому номеру, нормативных документов по обозначению и
помещений по идентификации.

`.docx` и `.xlsx` собираются своим кодом (ZIP без сжатия, `zipStore`) —
библиотек нет и быть не может, программа остаётся одним файлом без сети.

План ППР: 44 позиции из книги заказчика, 2026-2030. Периодичность —
доля года + вид ТО; доля подтверждена разметкой, номера ТО-1…ТО-4 не
расшифровываются (в книге их значения не написаны). Отметки о выполнении
— свой реестр `lnk_ppr`, ходит в обмене и в копии.

Проверка данных делит найденное на три уровня: ошибка (не может быть верным),
внимание (обычно недоделка), наблюдение (порядок заказчика неизвестен — не
называть ошибкой). Спорное в первые два уровня не попадает.

Акт: шапка о свидетельстве по центру курсивом (из настроек ЛНК); тип и
реквизиты контракта из карточки подразделения по году акта; разделы
перечня пронумерованы; номера протоколов неразрывны (в Word —
`w:noBreakHyphen`, не пробелы); подписи трёх ролей (руководитель
экспертной организации с организацией второй строкой, руководитель работ,
специалисты); колонка должностей — по самой широкой строке в ней (замер
через canvas настоящим шрифтом документа, `твипыСтроки`/`ширинаДолжностей`),
с пределом 4536 твипов = 8 см ШИРИНЫ колонки (не «8 см от края листа» —
при таком чтении предел выходил 5,25 см и «Заместитель начальника ЛНК»
переносился); должности по центру, фамилии вправо; `keepNext` + `cantSplit`
не дают подписям уехать на пустой лист; `keepLines` не даёт разорвать
раздел перечня между страницами. В HTML те же правила — `break-after:avoid`
на последнем разделе (класс «последний») и `break-inside:avoid` на разделах
и таблице подписей.

Номера объектов при группе одного наименования: сначала все заводские,
затем все регистрационные. При разнотипных объектах номера остаются при
своём объекте.

Падежи не склоняются автоматически. Для подразделения — поле «предложная
форма» в карточке. Для объектов — словарь `lnk_padezh`: форма запоминается
за НАИМЕНОВАНИЕМ (уникальных 127 на 315 записей), ходит в обмене,
заполняется в акте под фразой об объектах.

Висячие слова: `типографика()` ставит неразрывный пробел после
однобуквенных слов и коротких предлогов, между числом и единицей, после
знака №, перед «г.», между инициалами и фамилией. Применяется и в Word, и
на экране. Поля акта должны быть `display:inline` — при `inline-block`
Chromium переносит строку по границе блока и неразрывный пробел не спасает.

Размерность со степенью (м³, см²) — закрытый список единиц
(мм|см|дм|км|м)([23]), `разбитьСтепени`; в Word `w:vertAlign superscript`.
В поле ввода сохраняется обычное «м3» (innerText не видит <sup>).

Порядок элементов OOXML, на котором уже трижды ловился: `tabs` ПЕРЕД
`spacing` в pPr; `tblLayout` ПОСЛЕ `tblBorders` в tblPr; `vertAlign` ПОСЛЕ
`sz`/`szCs` в rPr. Таблица подписей требует `tblLayout fixed` — иначе Word
пересчитывает ширины по содержимому и переносит должность на вторую
строку.

Акт, число документов: при одном документе по методу — единственное число
названия и один знак «№». Формы единственного числа (`ДОК_ИМЕНА_ЕД`) — мой
черновик, в образцах их не было; правятся и хранятся отдельно от
множественных.

Право выдачи номеров закрепляется автоматически за местом, которое первым
выдаёт номер, если оно ничьё (`правоЕслиНичьё`). Блокировка остаётся только
когда право у другого места — иначе на первом запуске это выглядит поломкой.

Номер акта в форме записи выбирается: существующий (список от большего
номера), новый (следующий по порядку) или без акта. Объекты в списке — со
строкой «наименование, зав. № …, рег. № …», поэтому поиск по номеру
работает штатным механизмом браузера; при сохранении строка разбирается, а
карточка ищется по имени ВМЕСТЕ с заводским номером.

Задачи (`lnk_tasks`): одна сущность со сроком, периоды — шесть
представлений одного списка (`границыПериода`), не шесть списков. Горизонт
планирования — отдельное поле. Состояния: назначена → принята → выполнена →
закрыта, с возвратом на доработку; ставит и принимает место с признаком
`начальник` в `getWS()`. Перенос срока ОБЯЗАН сохранять `срок_первый` —
иначе отчёт всегда показывает сто процентов в срок (`вСрок`).

Производные задачи (`производныеЗадачи`) НЕ хранятся, а вычисляются из
плана ППР (срок — последний день месяца), дат поверки и сроков лаборатории.
Отмечаются в своих разделах: отметка в ППР сразу меняет их состояние в
списке задач. Журнал в производные не включён намеренно — он уже в
«Проверке данных», иначе дубль.

Повторяющиеся задачи: при приёме работы `продолжитьПовтор` создаёт
следующую со сдвинутым сроком, не выходя за `повтор_до`; защита от
задвоения — по паре `родитель` + `срок`.

Ответы заказчика по задачам: отчёт по форме (пришлёт позже — пока
внутренний вид), задачи назначает начальник, контроль исполнения нужен.

СДАНК-01-2020 и СДАНК-02-2020: заказчик прислал оба документа целиком —
прочитаны полностью (40 и 38 страниц), факты взяты дословно, без
домыслов. Сделано: классификаторы объектов (12 категорий, 63
подкатегории) и методов НК (12 категорий) из приложений — вшиты в
карточку лаборатории отдельными полями «область аттестации» (объекты +
методы), не путать со старым полем методов журнала, которое осталось
для сверки с тем, что реально делает лаборатория; ответственные лица
раздела 1 паспорта; аттестация специалиста дополнена датой и органом,
выдавшим удостоверение (нужны для Формы 1 паспорта); отдельный блок
«удостоверение о проверке знаний правил безопасности» у специалиста —
СДАНК-02-2020 прямо требует его отдельно от квалификационного, без него
квалификационное недействительно; Паспорт ЛНК — печатная форма (все 11
разделов) и выгрузка в Word, разделы 1–5, 9–10 из настоящих данных
программы, 6–8 и 11 — с честной пометкой, что заполнить нечем (раздел 5
на эти категории не делит, а передвижных лабораторий в программе нет
вовсе). Номер свидетельства об аттестации ЛНК
— «№ ЛНК-ХХХ Х ХХХХ» (раньше в программе стоял другой, придуманный
формат — исправлено); срок действия свидетельства НЕ фиксирован
документом, его каждый раз определяет комиссия по аттестации — программа
больше не предполагает срок сама. Подробности, включая точный текст
классификаторов и что именно взято из каких приложений — в
`ТЗ/СДАНК_что_нужно.md`.

Импорт из Excel (объекты, приборы): свой шаблон-таблица (кнопка рядом с
импортом создаёт пустой .xlsx с колонками из `REGS[kind].fields`), не
исходная книга заказчика — там формулы и разметка под `export_json.py`,
смешивать с формой ручного заполнения нельзя. Разбор .xlsx свой, без
библиотек: ZIP-каталог по сигнатурам PK руками (`zipЧитать`/`zipТекст`),
распаковку DEFLATE делает браузер (`DecompressionStream('deflate-raw')`)
— своего инфлейта не пишу, слишком велик риск ошибиться на настоящем
файле. Два бага, пойманных на РЕАЛЬНОМ файле от openpyxl (Excel мог бы
дать те же формы): тип ячейки `t="inlineStr"` — с заглавной, регэксп на
`[a-z]+` его не ловил; кириллица приходит как числовые ссылки
(`&#1053;`), не сырым UTF-8 — оба случая не годится проверять на файле
собственной генерации, там этих форм не было. Колонки сопоставляются по
ТЕКСТУ заголовка с `f.l`, не по номеру — переставленные столбцы не
ломают импорт. Даты СИ разбираются и как серийное число Excel (день 0 =
30.12.1899, поправка 25569), и как текст «31.12.2026». Импорт только
ДОБАВЛЯЕТ записи; проверка данных на дубли объектов теперь настоящая, а
не по совпадению имя+зав (это давало ложные срабатывания на карточках,
различающихся регистрационным номером): одинаковый непустой
зав./рег. номер у разных карточек — ошибка, одинаковое имя вовсе без
номеров — только наблюдение.

Подразделение у объекта (`подразделение` в карточке объекта, тип поля
`podr` — выпадающий список из справочника «Подразделения», значение —
ссылка на карточку, как и `a.подр` у акта, не текст): каждый объект
«принадлежит» подразделению, поэтому акт при первом открытии сам
подставляет `a.подр`, если у ВСЕХ объектов акта оно одно
(`автоподразделениеАкта`) — только при первом открытии, повторно не
трогает, если потом выбрали руками другое. Если объекты акта вразнобой
по подразделениям — ничего не подставляет и предупреждает текстом, какие
подразделения разные (`подразделенияАкта`, поиск по `объект_ид` в `O`).
В форме журнальной записи то же самое поле подставляется в `e_подразделение`
через `objHint()`, но только если поле ещё пустое — не переписывает
вписанное руками. Импорт объектов из Excel понимает колонку
«Заказывающее подразделение» как ТЕКСТ (название карточки), а не id —
ищет карточку по точному совпадению наименования (без учёта регистра);
не нашёл — оставляет пустым и перечисляет ненайденные названия в
диалоге подтверждения, а не подставляет что попало.

Инструктаж по охране труда — со слов заказчика, отдельный документ от
удостоверения ПБ (не путать: ПБ — это «проверка знаний правил
безопасности» из СДАНК-02-2020, инструктаж — общий, по ТК РФ).
Периодичность — раз в 90 дней (`ИНСТРУКТАЖ_ПЕРИОД_ДНЕЙ`), заказчик
подтвердил именно так, в СДАНК такого срока нет. Хранится ОДНА дата —
«прошёл в последний раз» (`инструктаж_дата` у специалиста), без журнала
прохождений: заказчик прямо сказал, что история не нужна. Срок «до»
считается прибавлением периода и оценивается через уже готовый
`срокЛаб()` (тот же bad/warn/ok, что у аттестации ЛНК — не плодил
отдельную копию). Проверка данных: дата не внесена — «внимание» (могли
не записать), а вот просрочка — «ошибка» (как просроченная поверка).
Заведено в `производныеЗадачи()` — попадает в «Задачи», если дата
внесена; без даты задачу строить не из чего, это только в «Проверке
данных». Статус виден и в списке специалистов отдельной колонкой.

Срок «до», если выпадает на нерабочий день, сдвигается на ближайший
рабочий день назад (по прямому указанию заказчика: инструктаж в
нерабочий день не проводится). Сначала это считалось просто от

Отдельная ловушка, из-за которой «просто добавить НД в обмен» было
нельзя: **id сидированных записей генерировались локально**
(`newId()` включает код места и время), поэтому у одного и того же
документа на М1 и М2 выходили РАЗНЫЕ id. Наивное добавление в обмен
дало бы 268 документов вместо 134, а ссылки на НД из «Методик контроля»
(они по id) на другом месте вели бы в пустоту. Сделано: канонический
`сидId(pfx,i)` — id вычисляется из позиции в сиде и одинаков на всех
местах; `каноническиеId()` переводит на них УЖЕ СОХРАНЁННЫЕ у заказчика
записи (ищет по естественному ключу — обозначение+наименование у
документа, идентификация у помещения, те же признаки, по которым
«Проверка данных» считает карточки дублями), а `заменитьСсылкиНД()`
переводит ссылки в методиках и в записях журнала. Плюс
`mergeСправочник()` — слияние с запасным ключом, чтобы один ГОСТ,
заведённый руками на двух местах, не задвоился; свой id при обновлении
сохраняется, потому что на него ссылаются наборы.

Попутно поймана СВОЯ регрессия, внесённая этими же правками, — поймана

на тот момент ещё не загружен — падала вся начальная загрузка, и до
пульта дело не доходило. Проявилось бы ровно у заказчика (там есть что
мигрировать), на чистой установке — нет. Исправлено двумя правками:
`setChrome` больше не падает на ещё не загруженном реестре (`ЗАД||[]`),
а сам перевод ссылок перенесён в конец инициализации.

Чтобы эта ошибка не повторилась, заведена самопроверка: `КЛЮЧИ_ДАННЫХ`/

«ошибка» показывает любой ключ памяти, который не попадает в сборку
копии. На нынешних данных молчит; на синтетическом «забытом реестре»
находит его сразу.

Из предложенных улучшений заказчик выбрал два — сделаны.

**Защита от потери незаполненной формы.** Журнальная запись, карточка
справочника, задача, карточка лаборатории и методика сохраняются только
по кнопке, а уйти из них можно тремя способами — закрыть вкладку,
нажать F5 и просто выбрать другой раздел в меню. Во всех трёх введённое
пропадало молча. Признак `_несохранено` ставится по первому же ВВОДУ в
поле (делегированный слушатель `input`/`change` на `#main`, он переживает
перерисовки, в отличие от слушателей на самих полях), снимается при
сохранении, удалении и при открытии другой формы (`формаСохранена()` —
13 точек). `switchView` спрашивает перед уходом (`уходСФормы()`), отказ
оставляет в форме; `beforeunload` просит подтверждения у браузера (свой
текст там показать нельзя, это ограничение браузера, не недоделка).

Клики по кнопкам «грязью» не считаются: они либо сохраняют сами, либо
перерисовывают только свой блок (`контрактПлюс`, `аттПлюс` и подобные
пишут в свои массивы по `oninput`, перерисовка их не теряет). Исключение
нашлось в карточке лаборатории: `допПлюс`/`допМинус`/`праздникПлюс`/
`праздникМинус` перерисовывают ВСЮ карточку и теряли правки остальных
полей — теперь тоже спрашивают. Раздел «Обмен файлами» в список видов с
формой НЕ включён намеренно: выбор файла для импорта — тоже `change`, и
иначе после каждого импорта выскакивал бы ложный вопрос.

**Проверка объектов без заказывающего подразделения.** Из подразделения
объекта акт подставляет своё (`автоподразделениеАкта`), пока оно не
проставлено — это приходится вписывать в каждый документ руками, и
узнаётся такое только при открытии акта. Сделано три случая, и главное
тут — не устроить шум: у заказчика 305 объектов и НИ ОДНОГО
подразделения, поэтому если справочник подразделений пуст вовсе, это
ОДНА строка про справочник («внимание»), а не 305 одинаковых замечаний
по каждому объекту. Когда подразделения заведены — «внимание» со списком
объектов, где поле пустое (первые 10, как везде в проверках). Ссылка на
удалённую карточку подразделения — «ошибка», по образцу такой же
проверки у `основной_ид` прибора.

Неотъемлемая часть поверяется вместе с основным прибором — прямое

даты у части НЕ редактируются и всегда берутся у основного прибора — то
же решение, что и с «действительно до» у аттестации специалиста, где
поле тоже перестало быть источником истины.

`синхронизироватьЧасти()` выставляет `поверка_дата`/`поверка_до` каждой
части по её основному прибору и зовётся на ВСЕХ путях, какими данные
попадают в `S`: при загрузке (рядом с оверлеем `ПОВЕРКА_ИЗ_ПАСПОРТА`),
после сохранения карточки прибора (`saveRegRec`), после импорта из Excel
(`импортПрименить`) и после приёма обмена или восстановления копии
(`применитьДанные`). Выравнивание безусловное, не «только если пусто»:
раз поле не источник истины, хранить расходящееся старое значение
незачем. Правка дат у ОСНОВНОГО прибора тянет за собой все его части
сразу, а не ждёт перезагрузки.

В форме прибора оба поля показываются `readOnly` с классом
`.отосновного` (приглушённый фон, курсор «нельзя») — как только в поле
«Неотъемлемая часть прибора» выбран основной прибор; при открытии уже
сохранённой карточки-части то же состояние ставит `частьВыбрана(z.основной_ид)`.
Снятие признака части возвращает полям обычный режим. Значения из
`readOnly`-поля `saveRegRec` читает как обычно, поэтому сохранение не
потребовало отдельной обработки.

Проверка «даты части не совпадают с основным» осталась (уровень

указание заказчика после того, как в панели было честно написано, что
на состав таблицы год не влияет. Теперь влияет: поле `месяц_поверки`
(одно значение на все времена) заменено на `месяцы_поверки` — объект
`{"2026":"Март","2027":"Сентябрь"}`. **Год, которого в объекте нет,
означает «в этом году не представляем»** — прибора в заявке и
плане-графике того года не будет; это же и есть признак отбора, каким
раньше был просто «месяц заполнен».

Новый тип поля карточки `type:"месяцы"` (как раньше появились `podr` и
`ref`) — не один `<select>`, а по списку на каждый год в строку. Из-за
этого `saveRegRec` получил отдельную ветку: у контейнера `rf_месяцы_поверки`
нет `value`, значения собираются из вложенных `rf_месяцы_поверки_<год>`,
пустые годы не хранятся вовсе. `частьВыбрана` — тоже: у неотъемлемой
части этот блок прячется и очищается по каждому году (раньше хватало
одного `поле.value=""`), иначе значение уцелело бы скрытым и всплыло в
документах.

Какие годы показываем — `годаПоверки()`: те же три, что предлагает панель
(текущий и два следующих), ПЛЮС любой год, который уже есть в данных;
иначе внесённый когда-то 2025-й молча пропал бы из вида. Редактор
«Проставить месяцы списком» получил колонку на каждый год сразу — править
по одному году значило бы переключать год панели ради каждой правки.

Миграция старого значения — названное допущение, а не факт из данных:
`мигрироватьМесяцыПоверки()` переносит прежний единственный месяц в
СЛЕДУЮЩИЙ год (на него подаётся заявка, на него же по умолчанию
открывается панель) и удаляет старое поле. Год при вводе нигде не
сохранялся — это и была та самая недоработка; другого года у того
значения нет. Перенос сразу виден: редактор показывает все годы разом.
Значение не из списка (опечатка) переносится как есть, не выбрасывается —
его показывает «Проверка данных». `изменено` миграция намеренно НЕ
трогает: каждое место мигрирует у себя само, а поддельно свежая отметка
перебила бы в обмене настоящую правку с другого места.

Что пересчитано по году: `месяцПрибора(п, год)`, `группыПоверки(год)`,
счётчики панели («2 из 41 приборов с месяцем на 2026»), заголовок колонки
предпросмотра, текст при пустой таблице, обе выгрузки Word. «Проверка
данных» на месяц не из списка теперь проходит ВСЕ годы записи, а не одно
значение: опечатка в 2028-м так же молча выкинет прибор из документов
того года, хотя на текущий год у него всё в порядке.

Excel остался обратимым: колонка одна — «2026 — март; 2027 — сентябрь»
(`месяцыТекст`), импорт разбирает тот же вид (`разобратьМесяцы`,
понимает и «2026: Март»), название месяца приводится к каноническому из
списка. Кусок без года («март») наугад никуда не подставляется — он
перечисляется в диалоге подтверждения, как ненайденное подразделение;
название с опечаткой, наоборот, кладётся как есть — молча потерянные
данные не покажет ничто, а опечатку покажет «Проверка данных».

Месяц и год представления на поверку теперь СЧИТАЮТСЯ от даты окончания
поверки — новое указание заказчика («так чтобы вовремя сдать прибор на
поверку и не допустить использования неповеренного прибора»). Это
разворот прежнего, тоже прямо подтверждённого решения («месяц — поле в
карточке, а не расчёт»), и разворот не бесплатный: на присланном
плане-графике 2025 из 15 приборов, которые есть и в картотеке, и в плане,
месяц представления совпал с месяцем окончания поверки только у 9. Об
этом сказано заказчику прямо, и поэтому ручной ввод НЕ выброшен, а стал
переопределением расчёта — иначе те шесть исключений записать было бы
негде. Хочет строго расчёт без исключений — скажет, уберу.

Расчёт: `месяцРасчётный(п,год)` = месяц даты окончания поверки минус
запас, дальше шагами по периодичности. Считается не датами, а номером
месяца (год×12+месяц): `Date.setMonth` у «31 марта минус месяц» даёт
3 марта из-за переполнения дня и молча возвращает не тот месяц.

**Запас** (за сколько месяцев до окончания представлять) — единственное
число, которого нет ни в каких присланных данных: сколько идёт поверка в
их ЦСМ, мне неизвестно. Поэтому не спрятанная константа, а настройка —
поле «запас, мес.» прямо в панели «Документы по поверке», хранится в
карточке лаборатории (`л.запас_поверки`, идёт в обмен), по умолчанию
1 месяц — наименьший запас, при котором прибор уходит на поверку до её
окончания. `saveЛабИзФормы` пришлось дополнить: она собирает объект
лаборатории заново из полей формы, а этого поля в форме карточки нет —
без явного переноса сохранение карточки его стирало бы.

**Периодичность** — `периодичностьПрибора(п)`: своё поле карточки
(«Периодичность, мес.»), а если пусто — интервал между «датой поверки» и
«действительно до» той же карточки. Это не догадка: на 20 приборах, чьи
даты пришли из настоящего паспорта, интервал выходит ровно 12 мес.
(15 приборов), 24 мес. (3) и 60 мес. (2). Ни у одного из 41 прибора поле
«периодичность» не заполнено вовсе, так что без этого вывода расчёт на
следующие годы не работал бы ни для кого.

Тут же поймана СВОЯ ошибка — тестом, не заказчиком: первая версия считала
интервал разностью номеров месяцев с поправкой «день меньше дня → плюс
месяц», и на настоящих парах вида 29.08.2024 → 28.08.2025 давала 13
месяцев вместо 12 (а 60 превращались в 61). Свидетельство действует «по
день до годовщины», и разность номеров месяцев на таких парах ошибается
в обе стороны. Переделано на разность в ДНЯХ, делённую на среднюю длину
месяца (30,436875) с округлением: на всех двадцати карточках выходит
ровно 12, 24 и 60.

Что изменилось для документов: признаком «прибор идёт в заявку и
план-график» стала не «заполненность месяца», а **известная дата
окончания поверки**. У заказчика это 20 приборов из 41 — у остальных
21 даты нет вовсе, и они теперь не попадают ни в один год (раньше не
попадали тоже — месяц у них никто не проставлял). Проверка «без даты
поверки» (уровень «внимание») существовала и раньше и теперь стоит
дороже; добавлена вторая — «периодичность не определена» («внимание»):
дата есть, а следующие поверки считать не из чего. На нынешних данных
она молчит, потому что у всех 20 период выводится из пары дат.

Просроченный прибор расчёт проектирует так, как будто его поверили в
срок — иначе следующих дат не из чего строить вовсе. Сама просрочка
видна отдельно: «Проверка данных» уровня «ошибка» и плитка на пульте,
обе были раньше и не тронуты.

Интерфейс: в редакторе «Проставить месяцы списком» и в карточке прибора
пустой пункт списка больше не «— нет —», а «— расчёт: май —» — видно,
что получится само; выбранный месяц перекрывает расчёт и подсвечивается
рамкой, возврат к расчёту — тем же пунктом. Карточка прибора показывает
ИТОГ по годам с пометкой «(вручную)» там, где расчёт перекрыт
(`месяцыИтогТекст`). В Excel-выгрузке приборов теперь две колонки:
ручные значения (их читает импорт) и «Месяц по расчёту (от даты
окончания поверки)» — только для чтения, её заголовок намеренно не
совпадает ни с одним полем карточки, иначе при первом же круге
«выгрузил — загрузил» расчёт застыл бы ручными значениями.

Наследование у неотъемлемой части расширено и заведён переключатель
«есть ли у прибора составные части» — два указания заказчика подряд.

`ПОЛЯ_ОТ_ОСНОВНОГО` (подставляются в ПУСТЫЕ поля, остаются
редактируемыми) пополнились четырьмя: `инв` (инвентарный номер),
`метод`, `хранение`, `состояние` — к прежним изготовителю, году
выпуска, дате ввода и владельцу. Комплект лежит в одном помещении и
живёт одной судьбой с основным прибором, но исключения бывают, поэтому
поля не запираются, в отличие от поверки.

Новое поле `составной` (`СОСТАВНОЙ_ДА_НЕТ` — «Да»/«Нет», обычный
`type:"select"`, сразу под «Неотъемлемой частью»): «Нет» убирает прибор
из списка выбора основного у ВСЕХ остальных карточек — у металлической
линейки составных частей точно нет, и предлагать её незачем. Отбор в
одном месте — `приборыСЧастями()`.

Пустое значение НЕ считается «нет», и это сознательно: иначе на первом
же запуске список родителей опустел бы у всех 41 прибора и отметить
часть стало бы нечем. Пусто — «ещё не указано», прибор в списке
остаётся; отмечать «Нет» заказчик будет по мере разбора картотеки.
У прибора, который сам является частью другого, `частьВыбрана` ставит
«Нет» при выборе основного — но только если поле ещё пустое, и поле
остаётся редактируемым: у датчика-комплекта свои части быть могут.

Попутно закрыта дыра, которую эта же правка и открывала: родителя могут
отметить «Нет» ПОСЛЕ того, как на него уже сослались части. Тогда его
пункта в списке нет, `select` показал бы пустоту, а сохранение формы
молча стёрло бы ссылку. Поле-ссылка получило необязательный `refВсе`
(полный список только для восстановления): выбранное значение
возвращается в список, даже если оно из него выпало. «Проверка данных» —
новое «внимание»: отмечено «составных частей нет», а части на прибор
ссылаются (в списке выбора его больше нет, иначе это нигде не всплыло
бы). Плюс обычное «значение не из списка» — тот же случай, что у
состояния и категории: импорт из Excel текст ячейки со списком не
сверяет.

**Настоящий баг, найденный своим же тестом, а не заказчиком, и живший в
программе с самого появления полей-ссылок.** Карточка, у которой поле
`podr`/`ref` уже заполнено, показывала «— не выбрано —», если id
записи — ЧИСЛО: в отрисовке стояло строгое `v===x.id`, а сохранённая
ссылка всегда строка («1» !== 1). Числовые id — ровно случай всех 41
прибора, 305 объектов и прочих записей из `данные.json` (их ставит
`export_json.py`), поэтому открыть карточку-часть и нажать «Сохранить»
означало ПОТЕРЯТЬ ссылку на основной прибор — молча. То же касалось
подразделения объекта и места хранения. Исправлено сравнением через
`String()` в обеих ветках отрисовки. Поймано тестом «пометил родителя
«Нет» → открыл часть → проверил select», а не осмотром кода: на глаз
`v===x.id` выглядит совершенно нормально.

Заодно список выбора основного прибора перешёл с `S` на `live(S)` —
раньше в нём были и удалённые карточки.

Excel-выгрузка приборов получила колонку «Есть составные части».

Заказчик попросил проверить, не потерялись ли старые связи частей — и
проверка вскрыла, что вчерашний фикс отрисовки полей-ссылок был только
ВЕРХУШКОЙ. Тот же разнобой типов ломал связь «неотъемлемая часть» ещё в
шести местах, и все они молчали.

Корень один и измерен, а не предположен: в `данные.json` у приборов,
объектов и специалистов `id` — **число** (`export_json.py` нумерует их
подряд), а любая сохранённая ссылка на карточку приходит из
`<select>.value`, то есть **строка**. `"1" === 1` — ложь, поэтому связь
считалась несуществующей везде, где стояло строгое сравнение. (Журнал и
план ППР не затронуты: там id строковые — «МИГР-2026-0001», «ППР-001».
Подразделение объекта и место хранения тоже: ПОДР и ПОМ заводятся руками
или сидированием, их id всегда строки.)

Замерено на живой программе ДО правки, а не выведено из кода: часть,
привязанная к сидированному прибору, не получала ни даты поверки, ни
номера свидетельства (`синхронизироватьЧасти` не находила основной
прибор); комплектность основного прибора оставалась пустой; в паспорте
не было строки «часть: …»; а «Проверка данных» показывала ЛОЖНУЮ ОШИБКУ
«ссылка ведёт в никуда или сама на себя». Последнее, вероятно, заказчик и
видел — отсюда и вопрос.

Исправлено не точечно, а одним правилом: `тотЖеИд(a,b)` (сравнение через
`String`) и `найтиПоИд(arr,ид)`; на них переведены все семь мест —
комплектность, синхронизация частей, паспорт (HTML и Word), проверка
расхождения дат, проверка битой ссылки (там же `S_ids` теперь хранит

Знак градуса и однотипные неотъемлемые части — два вопроса заказчика.

**Градус.** На клавиатуре знака нет, поэтому сделаны три равноправных
способа, и ни один не угадывает за человека: кнопка «°» в ряду символов
под полем (см. ниже), Alt+0176 на цифровой клавиатуре Windows и запись
**«^o»** — тем же знаком «^», которым в программе уже пишется степень:
«20^oC» печатается как «20 °C». Почему именно буква «o» (латинская) или
«о» (русская): степенью буква не бывает, подмена однозначна. **«^0» (ноль)
НЕ трогаю** — это может быть настоящая нулевая степень, гадать нельзя.
Подмена (`знакГрадуса`) идёт ДО разбора степеней, иначе «^o» стало бы
надстрочной буквой, а не знаком градуса.

Попутно исправлены два места в самой типографике, оба — настоящие, не
косметика. Первое: неразрывный пробел между числом и «°C» не ставился
вовсе — правило ловило голый «°», а следующая за ним латинская «C»
срывала его отрицательным просмотром вперёд; теперь в списке единиц есть
и «°C», и «°С» (русская С — заказчик может набрать любую). Второе: перед
голым знаком градуса программа ставила пробел («90 °»), хотя по ГОСТ
8.417 пробел нужен только перед единицей — «20 °C», а угол пишется
вплотную: «90°». Голый «°» из списка единиц убран.

(`КОЛ_КОД`). При импорте строка с кодом ложится в СВОЮ карточку, строка
без кода — новая запись, поэтому правка и добавление живут в одном файле.
Сверять по заводскому номеру было нельзя: он у заказчика не уникален,
подтверждено на настоящем паспорте («№ 640» стоит сразу у нескольких
наборов инструментов).

Три решения по ходу, каждое названо в диалоге подтверждения, а не
спрятано: **пустая ячейка НЕ стирает значение** (иначе случайно очищенный
или потерянный при правке столбец молча выкосил бы данные по всему
справочнику; сколько таких мест — показывается числом); **отметка
`изменено`/`место` ставится только реально изменившимся карточкам** (иначе
в обмен ушли бы все 41 как «правки» и перебили бы работу другого места);
**код, которого нет в справочнике, — строка пропускается и называется** (а
не добавляется новой записью: скорее всего это строка с другого места или
из удалённой карточки). Ссылки (подразделение, помещение) выгружаются
текстом и так же разбираются обратно, месяцы поверки — своей строкой по
годам, то есть круг обратим.

**1. Повторить запись журнала по объектам** (`размножитьОткрыть` и далее).
Одна и та же работа ложилась в журнал десятками почти одинаковых записей —
у заказчика 305 объектов, среди них дюжина однотипных теплообменников, и
каждая запись набивалась целиком заново. Теперь у сохранённой записи есть
кнопка «⧉ Повторить по объектам»: отмечаются объекты (с поиском по
наименованию и номерам) — на каждый создаётся своя запись. Переносятся
дата, статус, № акта, подразделение, исполнители по методам, отмеченные
приборы и НД, примечание. НЕ переносятся номера протоколов (их выдаёт
отдельный механизм с правом выдачи — чужой номер подставлять нельзя) и
имена файлов протоколов (у каждого объекта свой). id и `нп` — ровно как у
обычной новой записи (`newId()` без префикса, запись встаёт сверху).

Там же — **предупреждение о дубле при заведении новой карточки**
(`похожиеКарточки`): совпало наименование — программа показывает, какие
карточки уже есть, и спрашивает, добавлять ли. Только там, где одинаковое
имя действительно подозрительно (`ДУБЛЬ_ПРЕДУПРЕЖДАТЬ` — объекты, норм.
документы, помещения, подразделения); у приборов и специалистов этого нет
намеренно: два одинаковых люксметра и два однофамильца — обычное дело, там
вопрос был бы шумом. Это ровно тот случай, который висит в открытых
вопросах: «теплообменник 273ТНГ» заведён 12 раз.

**2. «Что изменилось»** — панель в разделе «Обмен файлами»
(`блокИзменений`, `измененияСписок`). Отметки `изменено`/`место` стояли у
каждой записи с самого начала, но показать их было негде: после приёма
файла не видно, что приехало с другого места, перед выгрузкой — что
уходит. Период — сутки / неделя / месяц / **с последнего приёма файлов**
(берётся из уже хранимой отметки `lnk_last_import`). Список по разделам,
у каждой строки место и время, клик по заголовку раздела открывает сам
раздел. Удалённые записи показываются отдельной пометкой — их больше не
видно нигде, а знать о них нужнее всего. Выгрузка в Excel — тем же
`xlsxФайл()`, что и остальные списки.

**3. Единый поиск по всей базе** — свой пункт меню «Поиск по базе» и
Ctrl+K (`renderНайти`, `найтиПоВсем`). Поиск в программе был в каждом
разделе свой, поэтому «где встречается этот заводской номер» означало
обойти восемь разделов подряд. Теперь одно поле ищет по журналу (включая
номера протоколов, исполнителей и № акта), объектам, приборам,
специалистам (включая записи аттестаций), подразделениям (включая
контракты), норм. документам, помещениям и задачам; результаты
сгруппированы по разделам, строка открывает саму карточку. Минимум два
знака — иначе на «1» выдало бы пол-базы. Удалённые записи не
показываются (их место — в «Что изменилось»).
